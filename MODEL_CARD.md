# Model Card — RockfallGuard Risk Models

Last updated: 2026-08-19

---

## Retraction of the previous accuracy claim

Earlier versions of this project's documentation claimed **99.5% / 99.83% accuracy**.
**That claim is withdrawn.** It should not be quoted in a README, a CV, or an interview.

It was not supported, for four independent reasons — any one of which is enough to
invalidate it:

**1. The training data was synthetic.** No real instrumented open-pit slope
measurements were used, because no such public dataset exists. The model was
therefore scored on how well it recovered a generating function that was itself
written by hand. Recovering your own function is not a prediction result.

**2. The reported metric measured a rule, not a model.** In `ml_engine.py` the
classifier's output is overridden immediately after it is produced:

```python
risk_level = class_labels[pred_class_idx]      # the classifier's answer
...
if risk_pct >= 65.0:                            # ...promptly discarded
    risk_level = "Critical"
elif risk_pct >= 35.0 and risk_level == "Safe":
    risk_level = "Warning"
```

The final label is largely a hardcoded threshold on the regressor's output. Any
end-to-end "classification accuracy" was substantially measuring that `if`
statement.

**3. The split was almost certainly not temporal.** Sensor readings are a time
series; consecutive frames are near-identical. A random train/test split places
frame N in train and frame N+1 in test, so the model is evaluated on data it has
effectively already seen. This single mistake inflates scores more than any
modelling choice, and it is the first thing an interviewer will probe.

**4. Accuracy was the wrong metric.** With realistic class balance (~3% Critical),
a model that predicts "Safe" unconditionally scores ~97% accuracy and catches
zero failures. A high accuracy figure on this problem is closer to evidence of a
broken evaluation than a good model.

### A separate and more serious issue: the CNN was never trained

`cv_engine.py` loads weights from `models/drone_cnn_model.pth`. That file is not
in the repository, and `get_cnn_model()` handles its absence by silently falling
back to a **randomly initialised** network:

```python
model = PitWallCNN()
if os.path.exists(weights_path):     # False -- file does not exist
    model.load_state_dict(...)
model.eval()                          # random weights, set to eval mode
```

Meanwhile the API response advertises:

```python
"cnn_architecture": "PyTorch PitWallCNN (Trained on Kaggle Drone Dataset)"
```

So `/api/analyze_drone_image` has been returning a risk score composed of ~50%
output from an untrained network and ~50% edge-gradient heuristic, labelled as a
trained model. **Fix this before demoing the feature to anyone**: either train the
CNN and commit the weights, or make the endpoint fail loudly when weights are
absent and correct the description string.

## Model 1 — Slope risk classifier and regressor

### Intended use
Demonstration and portfolio use only. **Not fit for deployment on a real mine.**
No output from this system should inform an evacuation decision.

### Architecture
- Classifier: `RandomForestClassifier` (200 trees, depth 12, `class_weight="balanced"`)
- Regressor: `GradientBoostingRegressor` → continuous 0–100 risk score
- 13 features (see `ml/train_model.py::FEATURE_NAMES`), `StandardScaler` normalised
- SHAP `TreeExplainer` for per-prediction attribution

### Training data
**Synthetic**, generated by `ml/train_model.py`. 40 simulated sites × 720 hourly
readings. The generator models:
- rainfall → antecedent 6h accumulation → pore pressure, with lag
- creep velocity by stability regime, with **overlapping** distributions
- persistent regime state (a slope does not flip hourly)
- machinery noise as a confounder (high seismic RMS, no instability)
- **silent failures**: ~18% of Critical states show suppressed precursors

Class balance is deliberately imbalanced (~89% Safe / ~8% Warning / ~3% Critical).

### Evaluation protocol
- **Temporal split, per site**: earliest 68% train, next 12% validation, latest 20% test
- Decision threshold for the Critical class tuned **on validation** for recall ≥ 0.85
- Reported on the held-out test set only

### Results (synthetic benchmark — not a real-world claim)

| Metric | Value | What it means |
|---|---|---|
| **Critical recall** | **0.79** | Caught 137 of 174 genuine failure states |
| **Critical precision** | **0.38** | Under half of Critical alarms were real |
| Critical PR-AUC | 0.63 | |
| Decision threshold | 0.16 | Tuned on validation, not test |
| Macro F1 | 0.66 | |
| Overall accuracy | 0.91 | **Do not quote alone** — see below |
| Risk regressor MAE | 3.25 pct-pts | |
| Risk regressor R² | 0.88 | |

**Read the first two rows together.** Overall accuracy is 0.91 while the model
misses roughly one in five genuine failures and raises about two false alarms for
every real one. That gap is the entire point: on an imbalanced safety problem,
accuracy is the least informative number available.

The low precision is a **deliberate choice, not a defect**. The decision threshold
was tuned down to 0.16 to favour recall. In this domain the costs are wildly
asymmetric — a missed failure can kill someone; a false alarm costs an unnecessary
evacuation and some operator trust. Tuning for recall and accepting the precision
cost is the correct trade-off, and alert fatigue is the real risk to manage.

### Limitations
- Trained on synthetic data. Real-world performance is **unknown**, not "similar".
- Never validated against a real slope failure.
- No calibration study; predicted probabilities should not be read as frequencies.
- Fixed 6-hour rolling windows, not tuned against real precursor timescales.
- Assumes clean, complete sensor input. No handling of dropout, drift, or failure.
- Site geometry is simulated; the model has seen no real pit.

### What would make this credible
1. Real instrumented slope data with confirmed failure/non-failure outcomes
   (see `DATA_SOURCES.md` — this is genuinely hard to obtain).
2. Validation against held-out **sites**, not just held-out time — the current
   split still lets the model see every site during training.
3. Calibration curves and a decision-cost analysis with real evacuation costs.
4. Prospective evaluation: predictions logged before outcomes are known.

## Model 2 — Drone imagery CNN

**Status: not trained. Do not present as a working model until this is resolved.**

`PitWallCNN` is a small custom architecture (3 conv blocks → binary sigmoid).
No trained weights exist in the repository. See the retraction section above.

To make it real, in order:
1. Pretrain on a public crack dataset (`DATA_SOURCES.md`).
2. Fine-tune on your own labelled drone imagery.
3. Report precision/recall on a held-out set of **your** images.
4. Commit the weights, or fetch them in CI from a release asset.
5. Change the response string to state what the model was actually trained on.

Until then, either remove the endpoint from the demo or label it honestly as an
edge-detection heuristic.

## How to talk about this in an interview

The withdrawn claim is now an asset rather than a liability. "I found the accuracy
claim in my own project was inflated, worked out the four specific mechanisms, and
rebuilt the evaluation" is a genuinely strong answer to *"tell me about a technical
mistake you made."* Most candidates have nothing concrete for that question.

Points worth being able to make unprompted:

- **"Why temporal split?"** — Adjacent sensor readings are near-duplicates. A random
  split leaks and inflates every metric. You caught it in your own work.
- **"Why is precision only 0.38?"** — Deliberate. Asymmetric costs. Tuned the
  threshold for recall on validation. You can discuss alert fatigue as the
  counterweight.
- **"Why not report accuracy?"** — 91% accuracy while missing 20% of failures. You
  have the confusion matrix to show it.
- **"What would break in production?"** — Sensor dropout, drift, distribution shift
  as the pit deepens, and silent failures the model structurally cannot catch.
- **"Is the model overfitting?"** — On synthetic data that question is almost
  beside the point; the binding limitation is that the data is not real. Being able
  to say *that* is more impressive than a defensive answer.

# Model 3 — Aerial terrain CNN (`PitWallCNN`)

Added 2026-10-14.

## What it does, and what it was advertised as doing

The repository shipped a `PitWallCNN` described as detecting "surface crack
propagation" and returning a "visual risk score". Two problems:

1. **There were no weights.** `models/drone_cnn_model.pth` did not exist, so the
   network ran randomly initialised.
2. **The published number was not a model output.** `cv_engine` computed
   `raw_cnn_score * 0.5 + (edge_intensity / 50.0) * 0.5` and presented the
   average as a percentage, attaching crack-severity strings by threshold. Half
   of that figure came from an arbitrary image-processing constant, and the
   other half from an untrained network.

Both are fixed. The model is now trained, and it reports the task it was
actually trained on.

## Why it is not a crack model

There is no crack-severity label anywhere in this repository. `data/annotation/`
contains stub files alternating between `{"shapes": []}` and a single hardcoded
`crack` rectangle at identical coordinates in every file — placeholders, not
labels.

The real labels, in `data/Open-Pit-Mine-Object-Detection-Dataset/annotation/`,
are 1,074 LabelMe files with a **single class** (`"1"`): rectangles around
open-pit workings in 1024×1024 aerial scenes.

Training a "crack severity" head on those labels would mean inventing the
target — the same category of error this document exists to retract. So the
model was trained on the task the labels support:

> binary patch classification — annotated open-pit mine region vs
> non-overlapping background crop from the same aerial scene

## Data and protocol

- 1,012 usable image/annotation pairs (62 skipped for having no usable box).
- 900 positive crops from inside annotated regions; 900 negative crops from
  windows in the same scenes with IoU ≤ 0.02 against every box.
- **Split grouped by source scene**, 406 / 87 / 88. Crops from one scene share
  sensor, lighting and terrain; a crop-level split would leak and inflate every
  number below.
- Preprocessing identical to inference: resize 224×224, `/255`, no ImageNet
  normalisation. A mismatch here degrades serving silently.
- Threshold tuned for F1 on **validation**, then frozen before the test set was
  touched.

## Held-out results

| | tuned (0.05) | default (0.5) |
|---|---|---|
| ROC-AUC | 0.956 | 0.956 |
| Accuracy | 0.873 | 0.790 |
| Precision | 0.854 | 0.977 |
| Recall | 0.909 | 0.606 |
| F1 | 0.881 | 0.748 |

Confusion at the tuned point: tp 129, fp 22, tn 112, fn 13.

The same reasoning as the rockfall model applies: at 0.5 the model is almost
never wrong when it says "mine", but misses 39% of them. The tuned point trades
12 points of precision for 30 points of recall. Both are published above so the
trade is inspectable rather than asserted.

**Do not quote the accuracy alone.** The test set is 276 crops from 88 scenes;
the 95% interval on accuracy is roughly ±4 points, so differences smaller than
that are noise. Grouped k-fold would be the honest next step before comparing
variants.

## What it does not claim

- Nothing about cracks, crack density or crack severity.
- Nothing about slope stability, failure probability or rockfall risk.
- Nothing about imagery containing no mine at all. Every training scene
  contained at least one, so negatives are *background within mining scenes*.
  The model has never seen a genuine negative scene.

## Serving

Inference scans overlapping windows at roughly a third of the frame's short
edge, rather than downscaling the whole frame to 224×224. The model sees crops
in training; a full scene squashed to 224×224 is out of distribution, and in
testing returned 0.5% confidence on a textbook open-pit image. The response
reports peak confidence, how many windows cleared threshold, and the peak
window's box, so a single hot tile is distinguishable from half the frame
lighting up.

## Reproducing

```bash
python ml/train_cnn.py        # seed 1337, 8 epochs, ~3 min on CPU
cd backend && python verify_cv.py
```

Writes `models/drone_cnn_model.pth` and `models/cnn_metrics.json`, the latter
carrying both operating points and an explicit `not_a_claim_about` list.
